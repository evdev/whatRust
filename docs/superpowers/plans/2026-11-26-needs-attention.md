# Needs Attention Inbox Plan

Needs Attention gives a business user a short list of customer requests and promises that still need action. Each suggestion shows who owes what, the message that supports it, and two actions, **Move to To-Do** and **Move to Follow-up**. The user chooses the decision provider and authorizes each account. Each account can set its active window, time zone, and check frequency. The default is once per hour from 07:00 to 01:00 the next day.

## What the user sees

- Put **Needs Attention** beside **Replies** in the selected account. Group suggestions by chat and show due work first. Give each card a short action label, a source quote, and **Open message**. If the message is unavailable, offer **Open chat** and say why.
- Show clear unanswered requests and unfinished promises in the main view. Give ordinary new requests one hour for a natural reply before badging them. An explicit deadline that would fall inside that grace period takes priority. Recheck queued replies before revealing a delayed card. Keep **Waiting on them** in a separate list until an explicit follow-up time arrives. For an undated wait, the user can choose a time. A future date stays visible without an overdue label. Ambiguous suggestions go to an optional **Review** view.
- Count actionable, unsnoozed suggestions in the badge. A refresh updates the existing card in place. Use a badge for suggestions and the existing alarm system for reminders the user explicitly saves. **Done**, **Snooze** and **Dismiss** act on an individual obligation. **Useful** and **Not useful** are available on every suggestion.
- Show *last successfully checked*, pending chats, and any coverage gap or pause. “All caught up” requires complete coverage of the enabled scope through the displayed time. Opening the inbox and giving feedback both work between scans.

## Scheduled checks and local timers

1. On first opt-in, record the start time and show it as the beginning of coverage. Start with new activity in the chosen account. Offer a separate, bounded lookback with a date range and cost estimate if the user wants to find work already open. Apply the same budget to backfill. Allow chat exclusions and individual group opt-in. In groups, retain the speaker and quoted-message relationship so a request to another member can be distinguished from one directed at the business.
2. While an eligible account is loaded and unlocked, capture new or changed inbound **and outbound** message references in a durable per-chat queue. Use the account, chat, full message identity and content revision to deduplicate events. An edit, revocation, or newly available transcript can change the evidence. Keep an ingestion position separate from the last successfully classified revision. Capture outside waking hours for the next scheduled pass.
3. Schedule checks from the start of the active window at the selected interval and in the selected time zone. An earlier end time falls the next day. Matching times keep checks active all day. Skip nonexistent scheduled times and run repeated local times once. Coalesce missed runs into one catch-up in the next eligible slot. The app must be running and unlocked to send content. Leave a sleeping account asleep and resume when its view is available. Existing catch-up covers only armed Stand-In chats or existing reply watches. Add discovery of changed eligible chats and page back to the last covered boundary, including chats first seen while offline. If the linked session cannot supply the missing range, display partial coverage. [Account sleep](../../../src-tauri/src/sessions.rs#L914) · [Stand-In catch-up](../../../src-tauri/resources/autoreply.js#L1628) · [Replies catch-up](../../../src-tauri/resources/todo.js#L2772)
4. Process a bounded queue fairly across enabled accounts and chats. Include a short overlap, any quoted message needed for meaning, and evidence for open obligations in that chat. Keep unprocessed pages pending when a request or run limit is reached. Commit results and the processed position together, up to the revision actually evaluated. A new message during a request remains queued. If it could change the decision, defer publishing that result until the new revision is checked. Recheck account consent, lock state and item revisions before applying results so a late response cannot undo a user action.
5. Independently advance due and snooze times **locally**. For example, a Friday follow-up becomes visible on Friday even if the customer has been silent since Monday. Make automatic suggestions badge-eligible during waking hours and catch up overdue timers on unlock or wake. User-set destination alarms follow their saved times. A tick with no pending classification makes **zero provider calls**, including when it only releases snoozes. A remediable provider failure retains pending work. Evidence that is simply ambiguous waits for a change or manual review instead of consuming tokens every hour.

## What the model decides

The app selects eligible conversations from activity. The model judges meaning. Consider every new substantive message, including statements without a question mark. Split long turns into numbered sentences or clauses locally and include their surrounding exchange. For each changed conversation, assign short request-local references to messages and candidate passages, include order, time and speaker role, and collect only existing transcripts. Represent missing media as unavailable evidence. Treat chat text as quoted data throughout. Provider output can propose inbox changes. Only a user action can create a task, set an alarm or transfer a suggestion.

| Decision | Inputs and allowed outcomes | What the app does |
| --- | --- | --- |
| Does this passage create work? | Evaluate each new request or promise against the surrounding chat. Allow business owes a reply or action, waiting on the customer, no obligation, and insufficient evidence. Evaluate separable clauses independently. | Create a local obligation only with attributable source evidence. One message can support two items of the same kind. An unclear split goes to Review. |
| Does it refer to existing work? | Offer the relevant open, dismissed and recently closed obligation IDs from this chat, plus **new** and **unclear**. Reuse the source passage and quoted-reply links. | Keep a stable local ID through clarifications, rescheduling and changes of who owes the next action. Ambiguous matches cannot merge items. |
| Does later evidence resolve it? | For each affected obligation, ask whether it remains open, changed, was fulfilled or cancelled, or has insufficient evidence. Select the specific later supporting passage from supplied choices. | Require a separately calibrated, stricter threshold and later evidence about that obligation to close it. Otherwise retain the last supported state. Keep automatic closures in reviewable history with **Reopen**. |

Bundle independent questions about the same chat. A question that needs an earlier answer runs in a follow-up request only when necessary and within budget. Validate answer names, allowed values, probabilities and evidence references against that request and chat. Never let an answer choose an arbitrary stored ID. Treat a refusal or incomplete answer as unresolved for the affected obligation. Rank or close only on the probability for the intended answer, with thresholds calibrated separately for each adapter. A confident “no” is still a no. Render the original excerpt locally as the explanation. A truncated conversation or missing attachment can justify review, but cannot on its own close an item.

If Ana asks for a revised quote and the business promises to send it Friday at noon, keep one obligation. “Thanks” leaves it open. “Here’s the revised quote” with a matching reference can resolve it. If Ana also asks for an invoice, sending the quote leaves the invoice open. **Already handled** lets the user close work completed by phone or in person.

Resolve relative dates from the source message's timestamp, language, and known time zone. The existing calendar matcher recognizes English and Portuguese phrases containing an explicit clock time. Extract its pure parsing logic for reuse. Show a date-only phrase such as “by Friday” as quoted text for confirmation, and leave the alarm unset. Unsupported languages, ambiguous zones, and conflicting dates also wait for user input. [Current calendar matcher](../../../src-tauri/resources/calendar-actions.js#L32)

## Feedback and suppression

Apply learning locally, after the evidence check. Offer Undo on feedback, dismissals and moves. Keep one effective usefulness vote per obligation. A move after **Useful**, a double click, or a retry cannot give an item two votes. Reversing an action restores the prior vote. Ignoring a card supplies no signal.

| User action | Effect now | Effect on future suggestions |
| --- | --- | --- |
| **Useful** or a successful move | Keep the card or link it to its saved destination. | Raise similar, evidence-backed items in this account's ranking. |
| **Dismiss** / **Not useful** | Hide this obligation. Only **Not useful** records negative feedback. | Suppress repeats of this obligation. A new explicit request, changed deadline or changed responsibility can reopen a dismissed suggestion. A greeting, a replay or a provider switch cannot. |
| **Done** / **Already handled** | Close this obligation. **Already handled** also records a correction to the model's resolution decision. | Keep closure distinct from dislike. New work can create a new item. |
| **Snooze** / **Too soon** | Ask when to bring it back and release it locally at that time. | **Too soon** can teach timing for similar items. It never teaches that the work was irrelevant. |
| **Mute this kind** | Preview the exact account, chat and type and let the user confirm. | Apply that rule to future automatic suggestions. Show matching hidden items in a reviewable list. |
| **Mark as needs attention** | Add the missed item directly from its message, even if a learned rule hid it. | Record a positive correction and show which rule, if any, hid it. Manual items remain user-owned. |

For the first rollout, match preferences on account, chat, obligation type and direction. As a starting rule, three **Not useful** votes on distinct matching obligations can propose a mute. The user must confirm before that rule hides a different obligation. Positive examples adjust ranking within actionable items. Feedback can neither supply missing evidence nor override a user-set deadline. Show learned rules with their scope and reason. Undo or reset recomputes affected rankings and restores eligible hidden suggestions.

## Move to To-Do or Follow-up

Both actions are directly accessible on each card. Open a prefilled, editable draft and commit only on **Save**. Keep the source account, chat and message link. **Cancel** leaves the suggestion available.

| Action | Draft and destination behavior |
| --- | --- |
| **Move to To-Do** | Suggest a title from the source passage and any clear due date. Allow an optional reminder. Use this destination for work that must remain tracked until someone marks it done, such as delivering a quote. |
| **Move to Follow-up** | Save in **Replies**. Preselect **I owe a reply** or **Waiting on them** when clear, otherwise ask. Offer a reminder time. Explain that the next qualifying outgoing or incoming message in that chat can clear the watch, even on another subject. A watch has a reminder field and no due-date field. |

The current `todo_add` returns a snapshot and merges open records by message and item class. Both watch directions share a class, so adding the opposite direction can switch an existing watch. For transfers, add a save operation that returns the destination ID and looks up a durable obligation transfer ID first. Distinct obligations sharing one WhatsApp message must stay independently editable. If an older manual item already cites that message, offer **Use existing** or **Create separate** and preserve the existing fields when linking. Update message-menu lookups that assume one matching item to offer a choice when needed. Preserve ordinary manual saves, watch behavior, and optional message starring. [Current save and merge](../../../src-tauri/src/todo.rs#L1016) · [Reply clearing rule](../../../src-tauri/resources/todo.js#L370) · [Message-menu lookup](../../../src-tauri/resources/todo.js#L1038)

Record transfer intent before saving. Serialize competing moves for the same obligation. Persist a receipt in the destination file in the same atomic write as the item. Retain the receipt across later completion or deletion so a crash or repeat click cannot recreate it. Finalize the link, hide the card, and count feedback once after a successful save. On a full store, failed write or cancelled draft, keep the card and offer retry. **Undo** removes a newly created destination only while it is still as saved. If it was edited, completed or previously existed, keep it and tell the user. Mark the receipt undone, restore the card and prior vote, and make a later deliberate move a new operation. Offer to link a retained destination on that move. A moved item follows the destination's lifecycle.

## Implementation and release checks

| Work to deliver | Acceptance check |
| --- | --- |
| Account settings, collection and local store | Persist consent, per-chat ingestion and classification positions, obligation revisions, timers, feedback and transfer state. Cover restart, lock during a call, exclusion, account deletion, same IDs in two accounts, a sleeping account with a new chat, partial history, and both daylight-saving transitions. |
| Provider adapters and budget | Exercise each documented request and response shape with synthetic fixtures. Check missing answers, wrong-message evidence, ambiguous model decisions, context caps, authentication, refusals, throttling, ambiguous billing after timeouts, month rollover and overlapping requests near the monthly cap. An idle pass and an expiring snooze each make zero requests. |
| Inbox and user feedback | Cover a fresh request answered inside its grace period, a silent chat becoming due, overlapping work, a reschedule, a late transcript, a missing attachment, a group message to somebody else, and a “thanks” after a promise. Check that undo, reset, and a positive correction work after restart and provider change. |
| Destination saves and recovery | Cover one source with two tasks, an existing manual watch in the other direction, two clicks, competing destinations, a crash immediately after destination save, a full destination, and undo after a user edit. Verify both source navigation and normal destination alarms. |
| Quality, cost and rollout | Evaluate all three providers on the same synthetic or separately authorized, labeled conversations in chronological order. A live account's consent applies only to its chosen provider. Label what was knowable at each check and whether a reminder was timely. Split tuning and held-out sets by whole chat. Sample quiet chats, suppressed and unsurfaced work, and confirmed outcomes outside WhatsApp as well as visible cards. Measure actionable cards / surfaced cards, surfaced time-bound commitments / labeled time-bound commitments, wrong automatic closures / automatic closures, repeat dismissals and gross cost per active account. Report counts and uncertainty per provider and language. |

Start with a single consenting account in preview. Proposed pilot targets are at least 90% actionable surfaced cards, at least 90% recall of time-bound commitments, and at most 1% incorrect automatic closures on held-out cases. Report sample sizes and 95% confidence intervals alongside these proposed targets. Keep a provider in preview if its precision or recall misses target or the samples are inconclusive. Enable automatic closure only when the upper confidence bound for incorrect closure meets the target. Otherwise offer closure in Review for user confirmation. Adjust thresholds per model and question version using the tuning set, then recheck on held-out chats before enabling a release. A contact-center evaluation found that several decision models struggled to abstain, which makes quiet chats and missing-evidence cases particularly relevant here. [Contact-center evaluation](https://arxiv.org/abs/2611.22949)

## Preview implementation

Enable an account in **Settings → Needs Attention**. This preview records usage locally and proposes closures in **Review** for confirmation. The Rust suite covers provider formats, replayed edits, overlapping obligations, spending reservations, and transfer recovery. JavaScript tests cover date resolution and the existing To-Do and Replies flows.

The opt-in synthetic pilot makes billable calls. Run it with test project keys supplied through `WHATRUST_ATTENTION_OPENAI_KEY`, `WHATRUST_ATTENTION_GEMINI_KEY`, and `WHATRUST_ATTENTION_JEV_KEY`.

```powershell
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib attention_live_synthetic_pilot -- --ignored --nocapture
```

The synthetic pilot checks integration responses and reports counts for a few labeled examples. Live WhatsApp coverage and sufficient held-out conversations are still required for release calibration.
